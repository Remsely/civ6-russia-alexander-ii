# Релиз мода

Порядок выпуска (проверка, версия, package.py, тег, `gh release`, Workshop) - в `docs/ru/RELEASING.md`, проверка в игре - в `docs/ru/TESTING.md`; здесь только правила и грабли.

Пуш, тег и публикация выполняются, когда пользователь их запросил или уже разрешил в текущем контексте; повторно подтверждать то же разрешение не нужно. Если поручена только подготовка, не публикуй результат. Для GitHub и HTTPS-аутентификации используй `gh` по `docs/git-access.md`.

## Описание и оформление
- Коммит выпуска при слиянии в основную ветку (`main`/`master`) имеет заголовок `v<версия>: <описание на английском> (#<PR>)`, например `v1.5.0-alpha: Add an animated 3D model of Alexander II to the diplomacy screen (#1)`; номер PR — при наличии. Тело с описанием изменений и проверок — на английском. Заголовок и тело всех коммитов — на английском; рабочие коммиты следуют `docs/commit-conventions.md`.
- Описание каждого релиза: сначала полный английский текст, ниже полный русский. Готовь единый файл заметок для GitHub Releases; оба раздела должны описывать одни и те же изменения. `CHANGELOG.md` и `CHANGELOG.ru.md` обновляй отдельно.
- Имя в игре красится цветом из Civ6_ColorAtlas.xml (цвета палитры игроков в тексте невидимы); текущий выбор - в `civ6-leader-texts`. Описание и тизер - ключи `LOC_REMSELY_*_MOD_DESCRIPTION/TEASER` в обоих языках, абзацы через `[NEWLINE]`, списки через `[ICON_BULLET]`.
- Страница Workshop: `workshop/description.bbcode` (`[h1] [h2] [list] [olist]`), `workshop/workshop.json` (`visibility` 2 = скрытый), превью из `tools\make_preview.py`.
- GUID мода (`id` в `.modinfo`) между версиями не меняй: по нему игра узнаёт мод.
- BLP для обеих платформ собирает `tools/build.py` (cooker SDK, `--platform MacOS`). Работу на macOS не проверяли - не обещай её.
- Числа в описании (города, реплики, бонусы) сверяй с данными (`CityNames`, число тегов), а не с дизайн-документом: в первом релизе мы написали «список из 11 городов», хотя в моде 11 новых названий, а список России ванильный.
- При изменении пользовательских возможностей сверяй фактический код, подключение, манифесты и результаты проверок с затронутыми описаниями в игре, README, design, CHANGELOG, roadmap, Workshop и заметках релиза на обоих языках. Не называй прототип или неподключённую запись частью готовой сборки, а прежнее игровое подтверждение — проверкой новой реализации. Обновляй только относящиеся к задаче материалы.

## Почему так
Перед публикацией подготовь и проверь конкретный архив и описание. Если публикация ещё не разрешена, покажи готовый результат для решения; если она уже входит в поручение, не добавляй повторное согласование.
