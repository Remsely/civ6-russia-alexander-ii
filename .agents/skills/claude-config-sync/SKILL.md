# Синхронизация скиллов и правил проекта

## Скиллы: автоматические зеркала

Источник истины — `.agents/skills/` Codex. `.claude/skills/` и `.zcode/skills/` — зеркала: меняй исходный скилл, затем синхронизируй оба зеркала. Не меняй только зеркальную копию, иначе следующая синхронизация затрёт её.

```powershell
.venv\Scripts\python.exe .agents\skills\claude-config-sync\scripts\sync_claude_configs.py --check
.venv\Scripts\python.exe .agents\skills\claude-config-sync\scripts\sync_claude_configs.py
```

`--check` только показывает изменения и возвращает 1 при расхождениях. Синхронизация копирует все файлы каждого скилла, включая ссылки и скрипты; дополнительные файлы и скиллы в зеркалах не удаляет, а перечисляет. Если у общего скилла есть лишние файлы, проверка остаётся неуспешной до ручного решения. Запускай с синхронизацией после изменения `.agents/skills/` и проверяй результат.

Команда не перезаписывает `AGENTS.md`, `CLAUDE.md` или MCP-конфиги. Только при отдельной задаче на MCP можно добавить `--mcp`: это дополнительно синхронизирует `.mcp.json` → `.zcode/config.json` по схеме Z Code; перед записью проверь локальные изменения. Файл `.codex/config.toml` не затрагивается. `AGENTS.md` и `CLAUDE.md` — самостоятельные инструкции своих агентов, не зеркала.


## Правила: ручная синхронизация

После изменения общего правила проекта сопоставь инструкции агентов вручную. Скрипт выше синхронизирует только скиллы: его успешный `--check` не подтверждает совпадение общих правил.

1. Прочитай актуальные `AGENTS.md`, `CLAUDE.md` и локальный diff. Определи, какое положение изменено и относится ли оно ко всему проекту или только к конкретному агенту. Последние указания пользователя и принятые решения имеют приоритет; не выбирай версию только по дате файла.
2. Перенеси общее правило в соответствующие разделы обоих файлов, сохраняя одинаковый смысл. Исправляй только затронутые положения; не копируй файлы целиком и не удаляй несвязанные инструкции или чужие изменения. Имена агентов, особенности инструментов и другие специфичные настройки сохраняй раздельно.
3. Для Z Code сначала установи, какой файл правил он действительно читает: проверь существующие инструкции и настройки проекта; если они этого не определяют, используй документацию установленного инструмента. Не придумывай имя файла и не считай `.zcode/skills/` заменой общим правилам. Если Z Code использует уже обновленный корневой файл, отдельная копия не нужна. Если точка подключения не установлена, синхронизируй известные файлы и явно укажи, что применение общих правил в Z Code не подтверждено.
4. Повторяющиеся процедуры удобно хранить в общем документе со ссылками из инструкций, например `docs/git-access.md`. При изменении такой процедуры проверь актуальность ссылок и отсутствие противоречащих указаний в файлах агентов. Не выноси туда специфичные инструкции только ради формального равенства файлов.
5. Проверь diff: общее правило отражено во всех установленных точках подключения, специфичные разделы сохранены, противоречий нет. В отчете отдельно укажи ручную проверку правил и автоматическую проверку зеркал скиллов; отметь непроверенные инструменты. Выполни обязательную проектную валидацию. Коммит и пуш делай только в рамках пользовательского поручения.

Если изменен сам этот скилл, после ручной правки синхронизируй `.claude/skills/` и `.zcode/skills/` штатным скриптом и запусти `--check`. Ручная синхронизация правил не дает основания менять MCP-конфиги или глобальные настройки инструментов.
